# 规格转计划（spec → plan）

读取一份已接受的规格，分解为可实施、可验证的 PR 批次，产出经得起审问的四节计划。计划回答「怎么做、什么顺序、风险在哪、怎么证明」。

## 输入

- 规格文件路径（`intent/NNN-spec.md`），状态须为 accepted；若仍是 in-review，先提醒产品负责人完成两遍走评审再动笔。
- 若同号 `NNN-plan.md` 已存在，先确认这次是修订（保留结构，只改受影响部分）而非重复产出。

## 执行步骤

1. **读规格摘 R#**：把 R# 及其验收判据逐条摘出，作为批次覆盖基准——每个 R# 必须落到至少一个批次（服务端与 UI 双落点分别标注），无批次承载的 R# 即计划缺口。
2. **核现状**：代码库当前状态、设计稿是否已确认（前端批次的前置）、可用技术基线（如脚手架技能的结构基线）。每个批次的事实性前提都要有依据。
3. **分解批次**（核心判断，三条规则）：
   - **垂直切片**：每批切穿全部相关层（schema / API / UI / 测试），完成即可独立验证或演示；不以「先把某层全做完」为默认。
   - **粒度上限**：单批以一个新鲜会话上下文能装下为限；装不下就拆。
   - **前置声明**：每批显式声明 blocked-by（前置批次），无前置者可立即开工；漏声明即计划缺陷。
4. **写计划** `intent/NNN-plan.md`，头部含并行声明（当前仅单链时一行「与其他 open 链无变更文件交集」），四节缺一不可：
   - **变更的文件**：机器可解析的相对路径列表（代码块内、支持 glob）——PR⊆plan 检查的比对基准；结构说明附后；明确「不动」项。
   - **工作顺序**：每步（PR 批次）标注覆盖的 R#、随批测试（docstring 标注）、前置批次。
   - **风险**：含审问三问——可能破坏什么？哪一步风险最高？放弃了哪些备选？三问答案落入本节；点名的风险必须有承接批次或缓解动作，禁止「点名不管」。
   - **证明**：逐项对应规格测试缝与 R# 验收判据；前端面写逐项核验路径；跨服务验证（冒烟、持久化、幂等）标明 CI 归属。
5. **审问**：调用 grill-me 过三问与依赖链、粒度、证明链缺口（追问示例：测试是否随批？依赖是否闭合？最高风险步的缓解在哪？留给实施者拍板的点还有几个？）。
6. **自检并提交**：对照第 4 步结构与三查——每 R# 有批次、每批有前置、每风险有承接——后，把计划单独提交（中文 Conventional Commits）。

## 例外与纪律

- **宽重构例外**：横跨全库的机械变更（改列名、改共享类型）不强行垂直切片，走 expand–contract——新旧并存 → 按影响面分批迁移（每批 CI 绿）→ 无调用方后收缩，三个阶段各自成批并声明前置。
- **不替工程师做决定**：批次重排、范围取舍列为待决点交工程师；**批准是人工动作**（状态置 accepted），Agent 不得代改。
- **不扩大范围**：计划只排规格内的 R#；过程中冒出的新能力，提示另立意图。
- 配套技能：方案收敛可调用 think，审问用 grill-me，计划文档评审可用 check；后端批次参考 fastapi-fullstack-scaffold 的结构基线。
