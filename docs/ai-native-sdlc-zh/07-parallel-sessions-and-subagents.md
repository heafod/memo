# 并行会话与子智能体

> 课程：[The AI-native SDLC playbook](https://academy.claude.com/zh-CN/courses/ai-native-sdlc-playbook) · 阶段：阶段 3：构建 · 第 7 课 / 共 14 课
>
> 官方课程页：[https://academy.claude.com/zh-CN/courses/ai-native-sdlc-playbook/parallel-sessions-and-subagents](https://academy.claude.com/zh-CN/courses/ai-native-sdlc-playbook/parallel-sessions-and-subagents)

---

一名工程师可以同时驱动多条工作流。

**并行会话（parallel session）**是另一个完整的 Claude Code 实例，在自己的 Git worktree 中处理一项独立任务。每个独立会话对彼此一无所知，连接它们的唯一纽带是驾驭它们的工程师。

**一个[子智能体（subagent）](https://code.claude.com/docs/en/sub-agents)**在单个会话内部运行，是一个带自身上下文窗口和工具限制的受限助手，适合在多个任务中反复出现的作业，例如验证应用按预期运行。

并行会话提高了工程师可以同时推进的任务数量，而子智能体让每个会话专注于自己的任务。工程师的工作是统筹和评审它们全部。

## 有何变化

| 传统 | AI 原生 |
| --- | --- |
| 一名工程师一次处理一项任务，把一天/一周的很大一部分时间花在构建、测试和评审上。等待期间切换任务是可以的，但上下文切换太累人，很少有人愿意这么做。 | 一名工程师同时运行多个 Claude 会话，每个会话在自己的 worktree 里处理自己的任务。重复性作业变成拥有自身上下文和工具限制的子智能体。工程师的工作转变为编排，并最终变成构建和监控循环。 |

## 开始之前

- **前置条件**：`CLAUDE.md`，因为所有会话都会读取该文件。反馈回路（feedback loop）（**阶段 4：测试**）在这里也有帮助，因为当会话能自行验证工作时，需要的工程师监督就更少。
- **基础设施**：一个 Git 仓库（隔离来自 worktree），以及调优过的权限设置，让会话不会为组织认为安全的命令等待审批提示。

## 如何执行

1. 工程师把工作拆成触及不同文件的任务，借助计划模式（plan mode）策略（**阶段 3：构建**）中的计划来判断哪些工作是独立的。共享文件的任务在单个会话中一个接一个地执行。
2. 每个并行任务获得自己的 worktree，例如在一个终端运行 `claude --worktree feature-auth`，在另一个终端运行 `claude --worktree fix-rate-limit`。worktree 是在自己的分支上的独立检出，能防止会话在文件上互相冲突。
3. 两三个会话是合理的起步数量。实际上限是一个人能妥善评审多少条工作流，所以只有当评审跟得上时才增加会话。
4. 把重复性作业变成子智能体，以 `.claude/agents/` 中的 Markdown 文件定义，每个都有名称、何时使用的描述，以及它可触及的工具。例子包括：一个代码简化器（在主智能体完成后去除不必要的复杂性）、一个验证器（运行应用并检查行为）、一个研究者（探索代码库并回报结果，而不淹没主上下文）。把这些定义提交到 Git，让整个团队共享。

## 实际效果

`.claude/agents/verifier.md`：

```markdown
---

name: verifier
description: 在会话报告完成之前运行应用并检查变更是否正常
tools: Bash, Read

---
用 make run 启动应用。演练变更后的行为以及相邻的两条流程。
报告你运行了什么、看到了什么，以及任何与 plan.md 不符的行为。
不要修复任何东西；只报告。
```

## 治理考量

更多会话意味着更多输出，所以控制必须来自仓库中的配置。那里的钩子（hook）和权限设置适用于所有会话，而会话做了什么会被记录，并归因于运行它的工程师。

## 如何衡量

- **先行指标**：在评审质量不降的前提下，每名工程师的并发会话数（从 OpenTelemetry 导出统计），以及一天中用于统筹而非等待的时间占比。
- **滞后指标**：每名工程师每周合并的变更数，与根据 PR 历史得出的返工率一同解读。
