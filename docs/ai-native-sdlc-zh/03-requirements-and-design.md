# 需求与设计

> 课程：[The AI-native SDLC playbook](https://academy.claude.com/zh-CN/courses/ai-native-sdlc-playbook) · 阶段：阶段 2：设计 · 第 3 课 / 共 14 课
>
> 官方课程页：[https://academy.claude.com/zh-CN/courses/ai-native-sdlc-playbook/requirements-and-design](https://academy.claude.com/zh-CN/courses/ai-native-sdlc-playbook/requirements-and-design)

---

产品负责人批准 `intent.md` 后，Claude 接手并产出一份需求与设计规格。这一过程由组织针对品牌、安全、合规和 UX 编写的 [技能包（skill）](https://claude.com/blog/complete-guide-to-building-skills-for-claude) 引导。

产品负责人评审这份规格，但不亲自撰写。这一流程的目标是产出一份工程团队可以据此规划、且标出关注领域的规格。

前端工作是最清晰的例子。`intent.md` 一旦被接受，产品负责人就在 [Claude Design](https://claude.com/product/design) 中根据 `intent.md` 做出设计稿（mock），迭代打磨，然后导出到 Claude Code 去构建。

## 有何变化

| 传统 | AI 原生 |
| --- | --- |
| 需求与设计是由不同团队运行的独立阶段。分析师把想法正式化为需求，设计师再把需求解析回设计。这种分离是为了责任分明，但它缓慢且会丢失信息。 | 两个阶段在同一个提示（prompt）会话中完成。Claude 接收 `intent.md`，在组织技能包的约束下产出需求与设计规格，并标出关注领域。 |

## 开始之前

- **前置条件**：已写好的 `intent.md` 文件，品牌、安全、合规和 UX 策略已写成技能包。
- **基础设施**：一位有 Claude 访问权限的产品负责人。不需要工程技能。

## 如何执行

1. 产品负责人开启一个加载了组织技能包的会话，并附上 `intent.md`。
2. 产品负责人的提示指向意图、点明约束，并要求标出关注点。先手工运行，再把它固化为组织级的斜杠命令。之后把「intent 仓库中 `intent.md` 被接受」作为触发器：一个非交互任务在合并时触发，加载组织技能包运行这一轮，并把 `spec.md` 作为拉取请求（pull request）提交（**阶段 5：部署**中的 CI/CD 策略覆盖这部分管道）。从那时起，产品负责人第一次介入就是评审。
3. 由同一位产品负责人对照想法评审规格。规格是否解决了所述问题？`intent.md` 中的未决问题是否得到了回答或被带到后续？
4. 先处理标出的关注点，因为它们正是分析师会升级上报的点。产品负责人在工程团队看到规格之前，与每个关注点的策略负责人逐一对齐解决。
5. 把 `spec.md` 与 `intent.md` 一起提交。这两个文件记录了什么被要求、什么被决定。
6. 产品负责人决定规格和意图是否进入构建阶段，对于组织归类为较高风险的内容咨询技术负责人。这个决定总是由人类同事做出；接受规格正是启动**阶段 3：构建**中计划模式（plan mode）策略的动作。

## 实际效果

提示词：

> **提示词（Prompt）**
>
> 阅读所附的 intent.md，产出一份将其整合进我们现有代码库的需求与设计规格。应用你可用的技能包，让方案符合我们的品牌规范、安全策略和 UX 标准。把规格完整地写成 spec.md，随时可以交给工程团队。清晰描述任何关注点，尤其是你无法同时满足相互矛盾的策略之处。

这个例子背后的 `intent.md` 来自一家保险公司，它希望客户能在门户中看到理赔状态。其中，`claims-api` 是门户的后端，`claims-core` 是保存理赔数据的较旧的内部系统。上面的提示词把它变成了这份 `spec.md`：

```markdown
# 规格：理赔状态自助服务
来源：intent.md（J. Ortiz，理赔运营）。状态：待产品负责人评审。
应用的技能包：secure-api-review、brand-voice、portal-ux。

## 需求
- R1. 已登录客户能看到每笔未结理赔的状态、下一步和预期日期。
- R2. 状态为四种之一：已受理（received）、评审中（in review）、已批准（approved）、已支付（paid）。
- R3. 响应只携带这三个字段，没有其他。
- R4. 客户看到的内容至多 60 秒旧。

## 设计
- 在 claims-api 中新增端点 GET /claims/{id}/status，位于网关 JWT 之后。
- claims-api 从 claims-core 读取理赔。门户绝不调用 claims-core。
- 在门户理赔页新增 StatusPanel。它把每个应答缓存 60 秒。

## 意图中每条约束如何被满足
| 约束 | 满足方式 |
| :---- | :---- |
| 门户会话中不新增 PII | R3。三个字段在 schema 中均未标记为 pii。 |
| 仅使用现有认证 | 网关 JWT。无新登录、令牌或角色。 |

## 意图中的未决问题
- 第三方公估师是否也需要访问权限？未回答。作为关注点 1 留待后续跟进。

## 关注点
1. 公估师没有门户账号。授予他们访问权会破坏「仅使用现有认证」，因此本规格不包含他们。负责人：安全。
2. portal-ux 技能包要求每个状态都显示日期。brand-voice 技能包要求绝不可把付款日期表述为承诺。按现状我无法同时满足两者。提议标签：「预计日期（Estimated date）」。负责人：合规。
3. claims-core 每秒只允许 50 个请求。60 秒缓存应能让门户保持在限制之下，但还没有人做过压测。负责人：claims-core 团队。
```

需求被编号，这样计划和评审都能引用它们。关注点 2 让两个技能包相互冲突，这正是提示词要求 Claude 标记出来的那类矛盾。

## 治理考量

策略冲突不再是在数周后的评审中才被发现，而是在规格撰写的同时读取并应用现行策略。组织技能包作为规格的约束被应用。规格、产生它的提示词，以及生效中的技能包版本，都记录在版本控制中。产品负责人对规格签字确认，并把标出的关注点分发给指定的策略负责人。

## 如何衡量

- **先行指标**：同一变更的 `intent.md` 提交与 `spec.md` 提交之间的时间间隔（两个 Git 时间戳），与旧的需求加设计周期对比。
- **滞后指标**：构建开始后的需求返工。统计同一变更的首次 `plan.md` 提交之后才提交的 `spec.md` 数量。Git log 可以直接给出这个数字。
