# 将意图捕获为 intent.md

> 课程：[The AI-native SDLC playbook](https://academy.claude.com/zh-CN/courses/ai-native-sdlc-playbook) · 阶段：阶段 1：规划 · 第 2 课 / 共 14 课
>
> 官方课程页：[https://academy.claude.com/zh-CN/courses/ai-native-sdlc-playbook/capture-intent](https://academy.claude.com/zh-CN/courses/ai-native-sdlc-playbook/capture-intent)

---

作为软件开发流程起点的 `intent.md`，可以通过不同的途径进入：一个人有了想法、一个工单被提交，或者一次事件通过告警浮出水面**（见阶段 6：维护）**。

当一个人有了想法，他们会与 Claude 进行头脑风暴，产出一份 Markdown 原型规格（proto-spec）。在传统 SDLC 中，同一个人必须说服产品团队的一名成员与他们一起或代他们把想法写下来。

Claude 生成的原型规格是人类可读、版本受控的，并且可以被下一个阶段直接消费。原型规格以 `intent.md` 的形式保存。

无论意图源自事件触发还是某个人，适用的步骤都是一样的：产品负责人在 `intent.md` 提交之前，先评审并纠正智能体撰写的这份文件。

## 有何变化

| 传统 | AI 原生 |
| --- | --- |
| 一个想法要先经过积压条目（backlog）、用户故事（user stories）、故事点（story points）和细化会议，才能有人去执行它。每次交接都会转移所有权，因此最终到达工程团队的内容，与发起人本意已相隔数层。 | 发起人与 Claude 头脑风暴，并把结果写成 `intent.md`——一份用发起人自己语言表达的原型规格。这份产物包含想要什么、为什么，以及在哪些约束之下。重复性流程通过技能包（skill）编码。 |

## 开始之前

- **前置条件**：无。
- **基础设施**：为非工程师提供 Claude 访问权限（claude.ai 或 Cowork）；一份达成一致的 `intent.md` 模板；一个共享、版本受控的 intent 仓库，由产品负责人关注。对于单一产品，最简单的仓库就是产品代码仓库里的 `intent/` 文件夹。这种设置让产物链紧挨着由它派生出的代码。只有当意图跨越多个代码仓库时，专门建一个 intent 仓库才值得那份开销；而在 monorepo 中，它就是其中一个目录。**阶段 3：构建**中的「遗留系统」一节，介绍这个仓库如何与已经存有记录的 Jira 或需求工具关联。

这套设置对平台或工程团队来说是一次性任务。需要一名技术团队成员来搭建 intent 仓库，并决定谁可以写入，因为很多贡献者会来自组织各处。

一旦仓库就绪，没有 Git 经验的贡献者无需直接使用 Git。取而代之的是，通过一个接入版本控制系统（例如 GitHub）的连接器，Claude 可以从 claude.ai 或 Cowork 代他们提交 Markdown 文件。

## 如何执行

1. 发起人用自己的话向 Claude 描述问题。发起人可以描述他们现在做不到什么、谁会受到这个想法的影响、更好的状态是什么样，或者哪些不在范围内。不需要正式语言。
2. 头脑风暴，直到想法具体化。Claude 会问分析师会问的问题：范围、用户、约束，以及成功是什么样。
3. 请 Claude 使用组织的模板把结果写成 `intent.md`。模板可以由技术团队成员编码为技能包，并由一位负责人签字确认。它可以涵盖问题、提议的结果、受影响的用户和系统、约束以及未决问题。
4. 发起人纠正 Claude 误解的任何内容。
5. 把 `intent.md` 提交到共享仓库。作者和时间戳加入记录，产品负责人从这里接手这个想法。

## 实际效果

`intent.md`：

```
# 意图：理赔状态自助服务
作者：J. Ortiz（理赔运营）。状态：草稿。
## 问题
客户拨打联络中心电话询问理赔进展。
客服人员约三分之一的工作时间花在仅查询状态的通话上。
## 提议的结果
客户在门户中看到理赔状态、下一步和预期日期。
## 受影响的用户和系统
理赔客服人员、门户团队、claims-core API。
## 约束
门户会话中不新增 PII。仅使用现有认证。
## 未决问题
第三方公估师（loss adjusters）是否也需要访问权限？
```

## 治理考量

证据就是已提交的 `intent.md`，它记录了作者、时间戳和完整的修订历史。它记录在 intent 仓库的 Git 历史中。产品负责人负责批准；把意图送入**阶段 2：设计**的接受或拒绝决定，以合并或评审关闭的形式被记录下来。

## 如何衡量

- **先行指标**：从第一次对话到提交 `intent.md` 的时间，从 intent 仓库的 Git 历史读取，其中记录了作者和时间戳。预期是从数周的需求梳理与细化周期降到数小时。
- **滞后指标**：存活率，即产品负责人接受进入**阶段 2：设计**（而不是关闭）的 `intent.md` 文件所占比例。接受或拒绝决定以产物的合并或评审关闭的形式被记录下来。此外，统计在同一个变更第一次 `spec.md` 提交之后，对 `intent.md` 的修改次数。
