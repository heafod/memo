# 将 Claude Code 计划模式作为默认起点

> 课程：[The AI-native SDLC playbook](https://academy.claude.com/zh-CN/courses/ai-native-sdlc-playbook) · 阶段：阶段 3：构建 · 第 4 课 / 共 14 课
>
> 官方课程页：[https://academy.claude.com/zh-CN/courses/ai-native-sdlc-playbook/plan-mode](https://academy.claude.com/zh-CN/courses/ai-native-sdlc-playbook/plan-mode)

---

工程师以计划模式（plan mode）开启 Claude Code 会话，把**阶段 2：设计**中已批准的 `spec.md` 交给 Claude，让它与他们进行问答式访谈，迭代打磨计划，直到他们对计划满意为止。

## 有何变化

| 传统 | AI 原生 |
| --- | --- |
| 工程师阅读设计后直接开始写代码。变更将如何实施——具体到哪些文件、哪些测试——都留在工程师脑子里，至多写进工单评论。没有其他人可以评审。评审者看到的第一样东西是完成后的 diff，而到那时返工已经很慢。 | 工作始于 Claude 在计划模式中产出的书面计划——在该模式下它可以读取代码库而不改动任何东西。工程师在代码写出之前先修正计划，批准后的版本以 `plan.md` 提交，供后续阶段对照检查。 |

## 开始之前

- **前置条件**：意图产物（`intent.md` 或 `spec.md`，如果存在的话）；`CLAUDE.md` 文件有帮助。
- **基础设施**：可访问代码仓库的 Claude Code。

## 如何执行

1. 工程师以计划模式与 Claude 开启会话。
2. 工程师把 `intent.md` 和 `spec.md` 交给 Claude，请它产出一份实施计划，列出会变更的文件、工作顺序，以及用于证明其成立的测试。
3. 通过提问来盘问这份计划：这个变更可能破坏什么？哪一步风险最高？Claude 选择不去做的其他选项是什么？
4. 迭代，直到一个从未看过这段对话的工程师，也能仅凭计划实施这个变更。
5. 把批准的计划以 `plan.md` 提交。计划进入审计轨迹，PR 评审策略（**阶段 5：部署**）将把最终的 diff 与它对照检查。
6. 接受计划，让 Claude 实施。有了扎实的计划，实施往往一遍就过。
7. 当实施偏离计划时，在同一个提交里更新 `plan.md`。可以考虑用一个钩子（hook）来强制两者保持同步。

## 实际效果

下面的计划针对一家保险公司的变更：在客户门户中增加一个显示理赔状态的面板。该面板调用门户后端 `claims-api`，后者从较旧的内部系统 `claims-core` 读取数据。

`plan.md`：

```markdown
# 计划：理赔状态自助服务（来自 intent.md 和 spec.md）

## 变更的文件

portal/src/claims/StatusPanel.tsx（新增）、claims-api/routes/status.py、claims-api/tests/test_status.py

## 工作顺序

1. 在现有认证之后新增状态端点（R1、R2、R3）。
2. 面板对接端点，带 60 秒缓存（R1、R4）。
3. 接入门户导航。

## 风险

claims-core API 以 50 rps 限流；面板必须缓存（规格关注点 3）。

## 证明

test_status.py 覆盖四种理赔状态（R2），并在出现任何多余字段时失败（R3）；截图与已批准的设计稿一致。
```

R1 到 R4 是 `spec.md` 中编号的需求，关注点 3 是 `spec.md` 标记出的一个风险。因为计划引用了它们，评审者可以逐行把计划与规格对照检查。

## 治理考量

设计评审发生在任何代码生成之前——那时改变方向仍然只是编辑一份文档的事。计划模式本身强制执行了这一点：在工程师接受计划之前，Claude 无法编辑文件。计划及其修订、以及谁接受了它，都被记录在案。常规变更由工程师批准，组织归类为较高风险的变更则交给技术负责人或架构师。

## 如何衡量

- **先行指标**：一次实施就完成合并的变更占比；从计划批准到 PR 合并的时间（所需数据在 PR 元数据中）。
- **滞后指标**：每个变更的返工轮次（同样来自 PR 元数据），以及合并后的 diff 仍然匹配已提交的 `plan.md` 的频率。

## 自动模式下的 Claude Code

Claude Code 也可以以[自动模式（auto mode）](https://www.anthropic.com/engineering/claude-code-auto-mode)运行：工程师对计划进行迭代和批准，之后 Claude 无需每次编辑都经过提示即可逐个应用变更。随着后续策略的护栏日趋成熟（调优的 `CLAUDE.md`、把策略编码为规则的技能包（skill）、能阻断危险操作的钩子（hooks），以及 Claude 可以运行的测试套件），自动模式会成为例行工作的默认方式：一份严密的 `spec.md`、一个小的爆炸半径（blast radius），以及已被测试覆盖的代码。

现在的转变是：从用户盯着智能体做编辑并逐一评审动作，转向在更长的自主会话之后评审产物。自动模式结合 worktree 使用时，还能进一步实现个人与团队层面的并行，并且是自主运行 SDLC、按**阶段 6：维护**所述完成闭环的基础。

## 遗留系统与事实源

现有的 SDLC 流程很可能已经在追踪产物，只是不用 Markdown 文件。工作项可能在 Jira，需求在自带监管可追溯性的工具里，设计在 Figma，变更审批则由变更委员会（change board）负责。这些系统很难被替换，因为审计人员和监管机构已经认可它们，其他团队也依赖它们，所以 AI 原生 SDLC 必须适配现状。对于流程产出的每一份产物，应当指定一个系统为事实源（source of truth），其他系统只保留副本或链接。

下面的配置可以建立单一事实源，且每个产物的选择可以不同：

- **以代码仓库为事实源**。Markdown 产物是权威记录，遗留系统引用提交中的文件。对工程主导的组织来说，这可能是最干净的配置之一：所有记录都存在于一个工具中，只有一个时间戳权威。
- **以遗留系统为事实源**。Jira、ServiceNow 或需求工具保存权威记录，Markdown 产物只是工作副本。Claude 在会话开始时读取记录，并在产生规格或计划的同一个会话中，通过模型上下文协议（MCP）连接器把结果写回。
- **以关联为最低要求**。所有产物都注明记录 ID，所有遗留记录都包含 Markdown 文件的提交 SHA。在向 AI 原生 SDLC 过渡时，关联选项是很好的起点，因为此时存在两个事实源。

只要两者之间有链接，或其中一方被声明为事实源，遗留系统与 AI 原生的 Markdown-first 系统就可以共存。
