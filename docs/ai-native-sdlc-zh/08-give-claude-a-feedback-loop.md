# 给 Claude 一个反馈回路

> 官方课程页：[https://academy.claude.com/zh-CN/courses/ai-native-sdlc-playbook/give-claude-a-feedback-loop](https://academy.claude.com/zh-CN/courses/ai-native-sdlc-playbook/give-claude-a-feedback-loop)

---

始终给 Claude 一种验证自己工作的方式，无论是测试、构建，还是截图对比。一个会话会在工程师看到错误之前，先检查自己的工作并修正自己的错误。

反馈回路不应与验证子智能体（**阶段 3：构建**）混淆。反馈回路贯穿整个任务，按工作所需运行任意多次。而验证子智能体是打包最终检查的一种方式：一旦会话认为工作已完成，就用一个全新的上下文窗口运行它。这样，结论就不会被产生代码时的那些假设所影响。

## 有何变化

| 传统 | AI 原生 |
| --- | --- |
| 代码能用的信号姗姗来迟。CI 晚几分钟、测试人员晚几天、生产环境晚几周。当智能体产出代码时，迟到的信号意味着必须有人检查它的全部输出，而这个检查的人就成了瓶颈。 | 会话在有人看到之前就获得检查自己工作的方式。运行测试、运行构建、截图。Claude 迭代直到检查通过，因此到达工程师手里的内容已经通过了检查。搭建这个回路是运行该会话的工程师的责任，下面的步骤就是为他们写的。 |

## 开始之前

- **前置条件**：无。
- **基础设施**：一套能在本地用一条命令运行的测试套件和一个构建。对于 UI 工作，让 Claude 看到结果的方式至关重要——要么是浏览器工具，要么是通过 MCP 接入的截图工具。

## 如何执行

1. 如果今天检查工作需要一串命令和一些环境知识，就把它们包装成单个目标，例如 `make test` 或 `npm test`，失败时以非零退出码结束。
2. 在 `CLAUDE.md` 的 Commands 一节中，列出每条命令，并附上健康输出的示例。
3. 设定一个目标并让它可量化，让 Claude 无需问你就能检查工作，例如：「`test_status.py` 中的全部测试通过」「截图与所附设计稿一致」「端点返回 200 并带新字段」。
4. 对于 bug 修复，先写失败的测试。请 Claude 把 bug 复现成一个测试，运行它，并确认它因为预期的原因而失败。提交那个测试。然后才请 Claude 在不修改测试的前提下让它通过，并用最后一步的测试文件钩子（hook）强制这一限制。一个在修复前就存在、且智能体无法改写的测试，就是 bug 已经消失的证据。
5. 对于 UI 工作，用视觉检查来闭环。给 Claude 一个浏览器或截图工具，给它设计稿，让它迭代。实现、截图、对比、调整。两三轮是正常的，而且结果应当每一轮都更好。
6. 让验证成为「完成」的一部分。这条指令写在 `CLAUDE.md` 中：「在报告任务完成之前运行测试，并展示输出。」
7. 最后，回路本身也需要保护，因为修复代码的智能体绝不能削弱对那段代码的检查。一个在修复任务期间阻断对测试文件编辑的钩子就能做到这一点。替代方案是在评审中检查 diff，拒绝任何触及测试的变更。

## 实际效果

`CLAUDE.md` 的验证模块：

```markdown
## 验证你的工作

- Build: make build（必须以「Build succeeded」结束）
- Test: make test（全部绿色；绝不要跳过或删除失败的测试）
- Lint: make lint（零警告）

在报告任何任务完成前运行全部三项，并粘贴输出。
如果某个测试失败，修复代码，而不是修复测试。
```

## 治理考量

- **强制执行什么**：任务报告完成前的验证，以及在修复期间禁止智能体编辑测试文件的限制——在组织希望保证这两点的地方，都以钩子实现。
- **证据是什么**：`make test` 的字面输出、构建日志，或 Claude 运行并粘贴的截图对比——证据来自工具链本身。
- **记录在哪里**：会话记录中（OpenTelemetry 导出会转发到组织的可观测性栈），以及 PR 的检查运行记录中（评审者和以后的任何审计人员都能看到）。
- **谁批准**：评审该 PR 的代码所有者，因为机械性证据已经附上，他们可以专注于意图和风险。

## 如何衡量

- **先行指标**：智能体编写的变更的 CI 首次通过率（CI 系统已支持统计）。
- **滞后指标**：每个 PR 的评审时间（来自 PR 元数据）——一旦测试接住了原本由评审者发现的那些问题，评审时间应当下降；以及来自事件跟踪器的变更失败率。
