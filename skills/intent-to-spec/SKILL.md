# 意图转规格（intent → spec）

读取一份意图文件，在与代码库和适用技能包对齐后，产出可评审的规格文件。规格解决意图陈述的问题，逐条回应约束，并把无法在规格层解决的问题显式升级为关注点。

## 输入

- 意图文件路径（`intent/NNN-<短标识>.md`），状态宜为「已接受」；若仍是「草稿」，先提醒发起人确认再动笔。
- 若同号 `NNN-spec.md` 已存在，先确认这次是修订（保留决策记录，只改未决部分）而非重复产出。

## 执行步骤

1. **读意图**：把问题、提议的结果、受影响的用户和系统、约束、未决问题逐项摘出。约束是硬边界，不得静默放宽。
2. **核代码库**：为「受影响的用户和系统」找到真实模块与文件。需求与设计中的每个事实性表述都要有代码依据——功能在哪、依赖有无、默认值是什么，逐一核实，不得凭空假设。
3. **选技能包**：从 `.agents/skills/` 与 `skills/` 中挑选适用技能，在规格头部「应用的技能包」列明。至少考虑 writing-for-agents（文档结构）；前端类变更加 frontend-design。未决问题需要发起人现场消解时，调用 `.agents/skills/grill-me` 追问；变更涉及领域建模（核心术语、长期结构决策）时，调用 `.agents/skills/grill-with-docs`，领域词汇沉淀至仓库根 `GLOSSARY.md`、决策记录至 `docs/adr/`。
4. **写规格** `intent/NNN-spec.md`，固定结构：
   - 头部：来源（链接同号意图，注明作者）、状态（待产品负责人评审）、应用的技能包
   - **需求**：编号 R1、R2…，每条注明对应模块，供计划与评审引用
   - **设计**：说明如何整合进现有架构
   - **意图中每条约束如何被满足**：表格逐条对照
   - **意图中的未决问题**：逐条标注「已回答（答案）」或「带出（去向）」
   - **关注点**：编号列出，每条必须写明负责人；技能包之间无法同时满足的矛盾必须写在这里，不得自行取舍
5. **自检并提交**：对照第 4 步结构逐项检查后，把规格与意图一起提交（中文 Conventional Commits），提交信息概述需求数与关注点数。

## 纪律

- **不扩大范围**：规格只解决意图陈述的问题；过程中冒出的新想法，提示发起人另立意图。
- **不替产品负责人做决定**：默认值、范围取舍等决策点列为关注点等待决策；决策做出后以「日期 + 决策人」追加到规格末尾的决策记录。
- **接受规格是人工动作**：状态改为「已接受」即触发进入构建阶段（计划模式起点），由产品负责人显式做出，Agent 不得代改。
