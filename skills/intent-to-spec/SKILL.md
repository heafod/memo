# 意图转规格（intent → spec）

读取一份意图文件，在与代码库和适用技能包对齐后，产出可评审的规格文件。规格解决意图陈述的问题，逐条回应约束，并把无法在规格层解决的问题显式升级为关注点。

## 输入

- 意图文件路径（`intent/NNN-<短标识>.md`），状态宜为「已接受」；若仍是「草稿」，先提醒发起人确认再动笔。
- 若同号 `NNN-spec.md` 已存在，先确认这次是修订（保留决策记录，只改未决部分）而非重复产出。

## 执行步骤

1. **读意图**：把问题、提议的结果、受影响的用户和系统、约束、未决问题逐项摘出。约束是硬边界，不得静默放宽。

2. **核代码库与原型**：为「受影响的用户和系统」找到真实模块与文件，每个事实性表述都要有代码依据，不得凭空假设。原型分两种成色，处理方式不同：
   - **工程师级原型**（结构规范、有校验与错误处理）：可提炼决策佐证——schema、状态机、类型形态等片段若比散文更精确，可内联进规格，但必须标注「来自原型」，且仅是佐证不是契约。
   - **演示级原型**（正常情况：只走通 happy path）：它是**提问器不是依据**——凡它没处理的边界（校验、异常、权限、口径），列为待讨论缺口，不得默认照抄。
   - 无论哪种成色：**规格的可实施性不得依赖原型质量**，业务约束必须由规格自身完备承载。

3. **选技能包**：在规格头部「应用的技能包」列明。至少考虑 writing-for-agents（文档结构）；前端类变更加 frontend-design。未决问题需要发起人现场消解时，调用 grill-me 追问；变更涉及领域建模（核心术语、长期结构决策）时，调用 grill-with-docs，领域词汇沉淀至仓库根 `GLOSSARY.md`、决策记录至 `docs/adr/`。

4. **合成与讨论**（修订模式先合成、后讨论）：
   - **合成**：已在意图、设计文档、既有决策记录中收敛的内容，直接蒸馏归位，不重新追问；追问只指向五问过不去的缺口。
   - **讨论**：议程固定为工程视角五问，逐 R# 过——① 验收判据（做到什么算满足）② 业务规则（校验、状态流转、权限、口径）③ 边界与异常（空态 / 失败 / 并发 / 超限）④ 数据语义（字段、生命周期）⑤ 非功能底线（安全、语言、性能）。
   - **归位**：每轮讨论结论必须落入四格之一——R# / 验收判据、决策记录（日期 + 决策人 + 结论）、关注点（带负责人）、未决问题（带去向）。四格更新完毕，讨论才算结束。

5. **写规格** `intent/NNN-spec.md`，固定结构：
   - 头部：来源（链接同号意图，注明作者）、状态、应用的技能包
   - **需求**：编号 R1、R2…，每条注明对应模块并**含验收判据**（供计划、测试与评审引用；测试 docstring 标注这些编号）
   - **设计**：如何整合进现有架构 + **测试缝**（在哪个接缝上验证：优先已有接缝、取最高可用接缝，接缝越少越好）
   - **意图中每条约束如何被满足**：表格逐条对照
   - **意图中的未决问题**：逐条标注「已回答（答案）」或「带出（去向）」
   - **关注点**：编号列出，每条必须写明负责人；技能包之间无法同时满足的矛盾必须写在这里，不得自行取舍
   - **决策记录**：决策逐条追加（日期 + 决策人 + 结论）

6. **自检并提交**：对照第 5 步结构逐项检查后，把规格与意图一起提交（中文 Conventional Commits），提交信息概述需求数与关注点数。

## 纪律

- **不扩大范围**：规格只解决意图陈述的问题；过程中冒出的新想法，提示发起人另立意图。
- **不替产品负责人做决定**：默认值、范围取舍等决策点列为关注点等待决策；决策做出后以「日期 + 决策人」追加到决策记录。
- **接受规格是人工动作**：状态改为「已接受」由产品负责人显式做出（两遍走评审通过 + 两段视角核对清单勾选注日期），Agent 不得代改。
- **三条讨论反模式**：蒸发（结论不落四格等于没达成）、流水账（spec 只留结论与理由，不粘贴对话过程）、以聊代闸（讨论消解不确定性，但不代替接受动作）。
