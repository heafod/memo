# intent/ · 意图仓库

所有产品变更从一份人类可读、版本受控的意图文件出发，沿固定管道推进。本文件是管道的唯一规则源；行数预算 150 行，超限即拆出 `RULES.md`、此处只留目的与索引。

## 管道

```
新想法 / 工单 / 线上事件
 └→ ① 意图 intent.md（发起人 → 产品负责人批准）
     └→ ② 设计稿 mock + 规格 spec.md（产品负责人主持与接受）
         └→ ③ 计划 plan.md（工程师产出与批准）
             └→ ④ 构建：Agent 写码 ⇄ 跑测试自证
                 （运行框架：AGENTS.md + skills + subagents + hooks + 测试套件）
                 └→ ⑤ 测试：确定性测试（反馈回路）+ 持续评估（evals，入 CI）
                     └→ ⑥ PR：Agent 多层评审 + diff 对照 plan
                         └→ ⑦ 部署：CI/CD + hooks 审批关卡
                             └→ ⑧ 维护：线上监控 → 新意图（回到 ①）
```

各阶段规则的载体：①②③ 本目录；④ `AGENTS.md` 与 `skills/`；⑤⑥ CI 与评审回路；⑦⑧ 部署与监控（随首条链建立）。逐阶段执行细节（调用的技能、产物在会话内的产出方式、失败补救路径）不在此预定义，随各阶段实际推进时在该阶段的活案例中确定。

## 文件约定

- `TEMPLATE.md` — 意图模板，新意图从它复制开始。
- `NNN-<短标识>.md` — 意图，链头，链级状态唯一承载处；头部标注作者与状态。
- `NNN-design.md` — 设计阶段产物（意图接受后、规格评审前）：已有成熟前端走「代码 → 设计稿」转换，否则直接生成；设计工具中立（Figma、ardot 等）。
- `NNN-spec.md` — 需求与设计规格，由 `skills/intent-to-spec/` 产出：R# 需求编号的出生地，供计划、测试与评审引用；必含「约束满足表」「未决问题去向」「关注点及负责人」三节（模板硬性要求；可行性核验不进 CI，由评审两遍走承担）。
- `NNN-plan.md` — 实施计划，规格接受后、实施前产出，四节缺一不可：**变更的文件**（机器可解析的相对路径列表）、**工作顺序**（每步标注 R#）、**风险**（含审问三问：可能破坏什么？哪一步风险最高？放弃了哪些备选？审问可调用 `.agents/skills/grill-me`）、**证明**（如何验证需求被满足，关链判据）。完成判据：从未见过讨论过程的工程师仅凭计划可实施。批准后方可实施；实施偏离计划时，计划与代码在同一提交中更新。
- `archive/` — closed 链的归档处（见「并行与归档」）。

## 状态机

文件级三态，英文 token、半角冒号书写（如 `状态: in-review`，括注中文说明允许）：

`draft`（起草中）→ `in-review`（在闸门待批）→ `accepted`（已生效）

迁移所有者见「角色与闸门」表：发起者提交即进 in-review，对应批准者批准即 accepted。

链级 `open → closed`，仅写在链头意图文件（`链: open`）。closed = plan「证明」节逐项核验通过（CI 绿、冒烟与设计稿确认等）；plan 批准或代码合并都不算。

修订回退：accepted 文件被修订，自身回 in-review，下游默认连带作废重审；确不影响下游（如改正错字）可显式豁免，理由记入该文件决策记录。

关链去向：closed 不重开；此后任何变更（含缺陷修复）开新链，来源标注工单或线上事件。「范围变化优先修订原意图」仅适用 open 期间的链。

## 角色与闸门

角色：发起人、产品负责人、工程师、技术负责人、评审者（代码所有者）、策略负责人，另设审批关卡（hooks·CI，非人，只执行规则不做判断）。当前一人兼任全部人类角色；映射随人员变化更新，角色语义不变。

| 产物 / 关卡 | 发起（产出） | 批准（闸门） |
| :--- | :--- | :--- |
| intent.md | 发起人（capture-intent 技能） | 产品负责人 |
| 设计稿 | 产品负责人主持制作与迭代 | 产品负责人迭代确认 |
| spec.md | 产品负责人触发（技能产出） | 产品负责人，评审两遍走（先发起人视角「是不是我要的」，再工程视角「能不能做、怎么证明」，一遍不过退回）；高风险咨询技术负责人；关注点与策略负责人对齐 |
| plan.md | 工程师（借 Agent 计划模式） | 工程师 |
| 代码 PR | 工程师 / Agent | 评审者（代码所有者）+ CI |
| 部署 | CI/CD | hooks 审批关卡 |

## 追溯

- R# 出生于 spec，仅链内唯一；跨链引用一律 `NNN/R#`（如 `001/R12`）。
- plan 工作顺序逐步标注 R#；测试文件 docstring 写覆盖范围、关键断言旁注 `# R12`（不进函数名）。
- 决策记录链内沉淀：文件内决策记录节 + Git 历史；跨链通用的决策升格进 `AGENTS.md` 或本文件。

## 自动化边界

判据：**自动化只做搬运与预填，不做判断**；判断闸门全部留人。

- 记为约定、暂不实施（当前由技能 + Agent 主动提示的半自动承担）：意图接受 → spec PR 骨架；spec 接受 → plan 草稿；PR 合并 → 部署；线上事件 → intent 草稿。
- CI 规则关卡（fail 即 block，随首条链在仓库根建立）：lint / format:check / backend 测试 / 前端 build / PR⊆plan 检查；evals 记占位，引入非确定性输出面（如 LLM 生成）时转实施。
- PR⊆plan 检查：PR 变更文件 ⊆ 对应 plan「变更的文件」清单；白名单（`.tmp/`、锁文件、生成物）放行；允许同 PR 修订 plan，新清单即时生效，plan 的 diff 由评审人把关理由；其余出圈即 block。

## 并行与归档

- open 链可多条并存；一个会话聚焦一条链。新链确定序号后立即提交空模板占位，防并行撞号。
- plan 必须声明与其他 open 链的变更文件交集：有交集（如都要改 `compose.yml`）声明先后依赖（「待 00X 关链后实施」）；无交集自由并行。PR 按链开分支；rebase 落后时 plan 清单随基线同步更新并留决策记录。
- 链 closed 时四个产物文件整体移入 `archive/`，设计稿导出物等执行文件随链归档；工作目录只留 open 链，目录即索引。本文件不记链清单；归档链检索用 `ls intent/archive/` 与 grep（R# 检索含 archive）。

## 意图粒度

- 一个新需求一个意图：设计稿、规格、计划都是该意图的阶段产物（`NNN → NNN-design → NNN-spec → NNN-plan`），不拆成独立意图。
- 新意图仅在新问题出现时创建：新想法、工单、线上事件（closed 链后的变更即属此类）。
- 范围变化优先修订原意图（决策记录留痕）；确属另一个问题（另一个发起人、另一份问题陈述）才另立新意图。
- 即便先有产品原型，也从意图开始：没有意图的原型，没有声明要解决什么问题。

## 工作流（意图捕获）

1. 发起人用自己的话描述问题（现在做不到什么、谁受影响、更好的状态、什么不在范围）。
2. 头脑风暴直到想法具体化：Agent 追问范围、用户、约束和成功标准。
3. Agent 按模板把结果写成 `intent.md`。
4. 发起人纠正 Agent 误解的内容。
5. 提交到本目录，产品负责人从这里接手。

本工作流由 `skills/capture-intent/` 技能固化执行。

## 治理

- 证据即已提交的文件：作者、时间戳、完整修订历史都在 Git 中；状态字段与提交记录即决定凭证。
- 规格应能追溯到来源意图；接受规格即启动计划阶段。

## 度量

- 先行指标：从第一次对话到提交 `intent.md` 的时间（目标：小时级，而非周级）。
- 滞后指标：进入设计阶段的存活率；同一变更首次 `spec.md` 提交后对 `intent.md` 的修改次数。
