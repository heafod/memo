# intent/ · 意图仓库

所有产品变更从一份人类可读、版本受控的意图文件出发，沿固定管道推进。本文件是管道的唯一规则源；行数预算 150 行，超限即拆出 `RULES.md`、此处只留目的与索引（数字可调，实质规则是「一次专注读不完即拆」）。

## 管道

```
新想法 / 工单 / 线上事件
 └→ ① 意图 intent.md（发起人 → 产品负责人批准）
     └→ ② 设计阶段：设计稿 ⇄ 可交互原型，迭代确认（同一交付物的两种呈现；
         无界面变更则产架构 / 接口设计）→ spec.md 冻结契约（R# 出生地）
         └→ ③ 计划 plan.md（工程师产出与批准）
             └→ ④ 构建：Agent 写码 ⇄ 跑测试自证
                 （运行框架：AGENTS.md + skills + subagents + hooks + 测试套件）
                 └→ ⑤ 测试：确定性测试（反馈回路）+ 持续评估（evals，入 CI）
                     └→ ⑥ PR：Agent 多层评审 + diff 对照 plan
                         └→ ⑦ 部署：CI/CD + hooks 审批关卡
                             └→ ⑧ 维护：线上监控 → 新意图（回到 ①）
```

② 内部次序固定为「设计确认在前，spec 冻结在后」：看与点（视觉回路）的反馈带宽高于读文字想象，「是不是我要的」放在设计回路上判断，spec 只冻结已确认的结果——先写 spec 后做设计，spec 必然跟随设计迭代反复修订。设计工具导出的代码是可执行的设计稿（转换源 / 参考实现），不因来源豁免生产判据：任何来源的代码过同一套关卡才算生产。

各阶段规则的载体：①②③ 本目录；④ `AGENTS.md` 与 `skills/`；⑤⑥ CI 与评审回路；⑦⑧ 部署与监控（随首条链建立）。逐阶段执行细节（调用的技能、产物在会话内的产出方式、失败补救路径）不预定义，按三条约定随活案例沉淀：

- 兜底：任何闸门失败 → 停、修根因、重跑同一闸门；plan / spec 本身有误 → 回上游修订（走修订回退）。
- 阶段卡：每阶段首次走通时记四行——进入条件 / 所用技能或命令 / 产物位置 / 失败检测与一条补救路径。
- 升格：阶段卡在该链关链前写入阶段归属处（技能 SKILL.md 或 `AGENTS.md`）并列入「证明」；同一错误第二次出现即强制固化，首次允许个案处理。

## 文件约定

- `TEMPLATE.md` — 意图模板，新意图从它复制开始。
- `NNN-<短标识>.md` — 意图，链头，链级状态唯一承载处；头部标注作者与状态。
- `NNN-design.md` — 设计阶段产物（意图接受后、spec 冻结前；**有界面面的变更才有**，无界面变更的架构 / 接口设计直接入 spec 设计节）：设计稿与可交互原型为同一交付物的两种呈现（静态稿 + 可点击 / 导出形态）；绿地直接生成，存量走「代码 → 设计稿」转换；设计工具中立（Figma、ardot 等）；导出代码 = 可执行设计稿，定位转换源 / 参考实现，非生产代码。
- `NNN-spec.md` — 需求与设计规格，由 intent-to-spec 技能产出：R# 需求编号的出生地，供计划、测试与评审引用；必含「约束满足表」「未决问题去向」「关注点及负责人」三节（模板硬性要求；可行性核验不进 CI，由评审两遍走承担）。接受前置：文件内两段视角核对清单（发起人视角／工程视角）均勾选并注日期。
- `NNN-plan.md` — 实施计划，规格接受后、实施前产出，四节缺一不可：**变更的文件**（机器可解析的相对路径列表）、**工作顺序**（每步标注 R#）、**风险**（含审问三问：可能破坏什么？哪一步风险最高？放弃了哪些备选？审问可调用 grill-me 技能）、**证明**（如何验证需求被满足，关链判据）。完成判据：从未见过讨论过程的工程师仅凭计划可实施。批准后方可实施；实施偏离计划时，计划修订与代码在同一 PR 内、但各自独立成提交更新。

## 状态机

文件级三态，英文 token、半角冒号书写（如 `状态: in-review`，括注中文说明允许）：

`draft`（起草中）→ `in-review`（在闸门待批）→ `accepted`（已生效）

迁移所有者见「角色与闸门」表：发起者提交即进 in-review，对应批准者批准即 accepted。

链级 `open → closed`，仅写在链头意图文件（`链: open`）。closed = plan「证明」节逐项核验通过（CI 绿、冒烟与设计稿确认等）；plan 批准或代码合并都不算。关链须留证：决策记录中逐项记「证明」结果与日期（含 CI 运行链接）；可由一条从未见过本链的全新 Agent 会话执行核验。

修订回退：accepted 文件被修订，自身回 in-review，下游默认连带作废重审；豁免须同时满足三条——① 仅限枚举低风险类（错字、格式、注释、非规范性文字；凡涉及 R#、约束或规范性条款不得豁免）；② 附影响清单：逐一下游文件标注受影响 Y/N，附上游 diff 与改动 R# 的 grep 证据；③ 豁免在下一道闸门置顶展示，由同一人在不同上下文复核一次。豁免与证据记入该文件决策记录。

关链去向：closed 不重开；此后任何变更（含缺陷修复）开新链，来源标注工单或线上事件。「范围变化优先修订原意图」仅适用 open 期间的链。

## 角色与闸门

角色：发起人、产品负责人、工程师、技术负责人、评审者（代码所有者）、策略负责人，另设审批关卡（hooks·CI，非人，只执行既定标准）。当前一人兼任全部人类角色；映射随人员变化更新，角色语义不变。角色名是视角标签而非真实职责分离——单人无法靠角色实现分离，真正的分离由关卡与闸门先后顺序保证。

| 产物 / 关卡 | 发起（产出） | 批准（闸门） |
| :--- | :--- | :--- |
| intent.md | 发起人（capture-intent 技能） | 产品负责人 |
| 设计稿 / 可交互原型 | 发起人或产品负责人主持（闸门在确认，不在谁动手） | 产品负责人迭代确认（发起人视角参与） |
| spec.md | 产品负责人触发（技能产出） | 产品负责人，评审两遍走（先发起人视角「是不是我要的」，再工程视角「能不能做、怎么证明」，一遍不过退回）；高风险咨询技术负责人；关注点与策略负责人对齐 |
| plan.md | 工程师（借 Agent 计划模式） | 工程师 |
| 代码 PR | 工程师 / Agent | 评审者（代码所有者）+ CI |
| 部署 | CI/CD | hooks 审批关卡 |

## 追溯

- R# 出生于 spec，仅链内唯一；跨链引用一律 `NNN/R#`（如 `001/R12`）。
- plan 工作顺序逐步标注 R#；测试文件 docstring 写覆盖范围、关键断言旁注 `# R12`（不进函数名）。
- 决策记录链内沉淀：文件内决策记录节 + Git 历史；跨链通用的决策升格进 `AGENTS.md` 或本文件。

## 自动化边界

判据分两层：人负责**制定标准**（lint 规则、eval 检查项与阈值、plan 清单、批准记录）；机器可对版本受控的既定标准做**机械执行**——计算、比对、查记录、不符即阻断，全程可审计。无法预先规则化的情境判断（问题对不对、规格够不够、风险接不接受）一律留人。反作弊不变量：被把关的一方不得在同一变更中修改把关标准或其读取的批准记录（故 plan 修订须独立成 commit，见 PR⊆plan）。

- 记为约定、暂不实施（当前由技能 + Agent 主动提示的半自动承担）：意图接受 → spec PR 骨架；spec 接受 → plan 草稿；PR 合并 → 部署；线上事件 → intent 草稿。启动条件：根 CI 首次全绿且开启第二条链；此后每季度复核一次是否仍搁置。
- CI 规则关卡（fail 即 block，随首条链在仓库根建立）：lint / format:check / backend 测试 / 前端 build / PR⊆plan 检查 / R# 存在性检查（测试标注的 R# 须在对应 spec 中存在）；evals 记占位，引入非确定性输出面（如 LLM 生成）时按上述两层判据转实施（机器执行人定阈值）。
- PR⊆plan 检查：以**最近一次 accepted 的 plan 清单**为比对基准（而非 PR 内改后的清单）；白名单（`.tmp/`、锁文件、生成物）放行。PR 内经 plan 修订新增的文件单列「实施中新增（逐条理由）」：少量新增（≤3 个文件，且不含顶级目录与保护路径 CI／infra／安全）可随评审通过；实质性扩圈则 plan 回 in-review 重批后方可合并。plan 修订独立成 commit（`docs(plan): 实施偏离更新`），不与代码混杂。

## 并行与归档

- open 链可多条并存；一个会话聚焦一条链。新链确定序号后立即提交空模板占位，防并行撞号。
- plan 默认声明一行「与其他 open 链无变更文件交集」；当第二条 open 链并存时升级为逐项核对：有交集（如都要改 `compose.yml`）声明先后依赖（「待 00X 关链后实施」），无交集自由并行。PR 按链开分支；rebase 落后时 plan 清单随基线同步更新并留决策记录。
- closed 链**不移动文件**：链头标记 `链: closed` 即归档态，路径永久稳定（仓库文档与跨链引用可放心深链）。open 链索引即 grep：`grep -l '链: open' intent/[0-9]*.md`；R# 检索全目录 grep。仅当链数超过约 50 条、目录浏览成本确成问题时，再引入 `archive/` 移动 + 同提交脚本重写全仓引用的机制。

## 意图粒度

- 一个新需求一个意图：设计稿、规格、计划都是该意图的阶段产物（`NNN → NNN-design → NNN-spec → NNN-plan`），不拆成独立意图。
- 新意图仅在新问题出现时创建：新想法、工单、线上事件（closed 链后的变更即属此类）。
- 范围变化优先修订原意图（决策记录留痕）；确属另一个问题（另一个发起人、另一份问题陈述）才另立新意图。
- 即便先有产品原型，也从意图开始：没有意图的原型，没有声明要解决什么问题。

## 工作流（意图捕获）

1. 发起人用自己的话描述问题（现在做不到什么、谁受影响、更好的状态、什么不在范围）。
2. 头脑风暴直到想法具体化：Agent 追问范围、用户、约束和成功标准。
3. Agent 按模板把结果写成 `intent.md`。
4. 发起人纠正 Agent 误解的内容。
5. 提交到本目录，产品负责人从这里接手。

本工作流由 capture-intent 技能固化执行。

## 治理

- 证据即已提交的文件：作者、时间戳、完整修订历史都在 Git 中；状态字段与提交记录即决定凭证。
- 规格应能追溯到来源意图；接受规格即启动计划阶段。

## 度量

- 先行指标：从第一次对话到提交 `intent.md` 的时间（目标：小时级，而非周级）。
- 滞后指标：进入设计阶段的存活率；同一变更首次 `spec.md` 提交后对 `intent.md` 的修改次数。
