# intent/ · 意图仓库

本目录是 Memo 产品的意图仓库（intent repo）：所有产品变更从一份人类可读、版本受控的 `intent.md` 原型规格出发。

## 文件约定

- `TEMPLATE.md` — 约定的 `intent.md` 模板，新意图从它复制开始。
- `NNN-<短标识>.md` — 每份意图一个文件，序号递增；头部标注作者与状态。
- `NNN-design.md` — 与同号意图配对的设计稿：前端类变更在设计阶段产出（意图接受后、规格评审前）；已有原型或成熟前端代码时走「代码 → 设计稿」转换，否则直接生成；设计工具中立（Figma、ardot 等，不绑定单一厂商）。
- `NNN-spec.md` — 与同号意图配对的需求与设计规格，由 `skills/intent-to-spec/` 技能产出：需求编号（R1、R2…）供计划与评审引用，须包含「约束满足表」「未决问题去向」「关注点及负责人」三节。
- `NNN-plan.md` — 与同号意图配对的实施计划，规格接受后、实施前产出：**变更的文件**、**工作顺序**（每步标注所满足的规格需求编号 R#）、**风险**（引用规格关注点）、**证明**（如何验证需求被满足）四节。计划评审必须过三问：这个变更可能破坏什么？哪一步风险最高？放弃了哪些备选方案？——三问的答案落入「风险」节，审问可调用 `.agents/skills/grill-me` 执行。完成判据：从未见过讨论过程的工程师，仅凭计划即可实施该变更。计划须经人批准后才可实施，批准与修订记录在 Git 历史；它是后续 diff 评审的对照基准。

## 意图粒度

- 一个新需求一个意图：设计稿、规格、计划都是该意图的阶段产物（`NNN → NNN-design → NNN-spec → NNN-plan`），不拆成独立意图。
- 新意图仅在新问题出现时创建：新想法、工单、线上事件。
- 范围变化优先修订原意图（决策记录留痕）；确属另一个问题（另一个发起人、另一份问题陈述）才另立新意图。
- 即便先有产品原型，也从意图开始：没有意图的原型，没有声明要解决什么问题。

## 工作流

1. 发起人用自己的话向 Agent 描述问题（现在做不到什么、谁受影响、更好的状态、什么不在范围）。
2. 头脑风暴直到想法具体化：Agent 会追问范围、用户、约束和成功标准。
3. 请 Agent 按模板把结果写成 `intent.md`。
4. 发起人纠正 Agent 误解的内容。
5. 提交到本目录，Git 历史记录作者与时间戳，产品负责人从这里接手。

本工作流由 `skills/capture-intent/` 技能固化执行。

## 治理

- 证据即已提交的 `intent.md`：作者、时间戳、完整修订历史都在 Git 中。
- 产品负责人决定接受或关闭；状态字段与提交记录即决定凭证。
- 接受的意图进入需求与设计阶段，产出的 `spec.md` 应能追溯到来源意图。
- 规格接受后先产出实施计划（`NNN-plan.md`），计划经人批准后方可实施；实施偏离计划时，计划与代码在同一提交中更新。

## 度量

- 先行指标：从第一次对话到提交 `intent.md` 的时间（目标：小时级，而非周级）。
- 滞后指标：进入设计阶段的存活率；同一变更首次 `spec.md` 提交后对 `intent.md` 的修改次数。
